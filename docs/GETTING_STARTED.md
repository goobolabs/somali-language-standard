# Getting Started

Welcome to the Somali Language Standard (SLS). This guide orients you in the
repository and tells you where to begin depending on who you are.

---

## Repository layout

```text
somali-language-standard/
├── README.md                  Project overview — start here
├── CONTRIBUTING.md            How to contribute
├── GOVERNANCE.md              Who decides what, and how
├── ROADMAP.md                 Milestones to the first public release
├── IMPLEMENTATION_PLAN.md     Phase-by-phase execution checklist
├── CHANGELOG.md               Release history (Keep a Changelog)
├── LICENSE-CODE               MIT — code, tools, schemas
├── LICENSE-DATA               CC BY 4.0 — all linguistic content
│
├── .github/                   Issue/PR templates, CI workflows
│
├── docs/                      Human-facing documentation
│   ├── ARCHITECTURE.md        ★ The master specification — source of truth
│   ├── GETTING_STARTED.md     This file
│   ├── STYLE_GUIDE.md         Writing and formatting conventions
│   └── FAQ.md                 Common questions
│
├── spec/                      Normative specifications — the standard itself
├── schemas/                   JSON Schema contracts for every record type
│
├── data/                      Hand-authored source data (all JSONL)
│   ├── lexicon/               The curated dictionary
│   ├── terminology/           Domain glossaries (20 launch domains)
│   ├── translation/           Parallel EN↔SO pairs
│   └── corpora/               Example sentences, rights-cleared text
│
├── ai/                        Resources shaped for AI consumption
│   ├── prompts/               System prompts and prompt templates
│   └── datasets/              Instruction / fine-tuning / correction data
│
├── benchmarks/                Evaluation suites (never mixed with training data)
├── tools/                     Rust validators; future compilers and exporters
└── examples/                  Integration guides for developers
```

Two structural rules to internalize early:

1. **Hand-authored vs. generated.** `spec/`, `data/`, `ai/`, and `benchmarks/`
   are hand-authored sources. Release bundles and derived artifacts are
   generated by tooling and never hand-edited.
2. **Benchmarks are quarantined.** Nothing in `benchmarks/` may also appear in
   training/fine-tuning datasets, to prevent contamination.

## Where to begin

**If you are a native speaker or linguist** — you are the most valuable
contributor this project can have. Read the [FAQ](FAQ.md) and
[CONTRIBUTING.md](../CONTRIBUTING.md), then watch for lexicon and terminology
work opening up in Phases 5–6 of the
[implementation plan](../IMPLEMENTATION_PLAN.md).

**If you are a developer** — read [ARCHITECTURE.md](ARCHITECTURE.md) §6–§8
(formats, schemas, naming) and §17–§19 (CI, tooling, API surface). Tooling
work begins in Phase 4.

**If you are an AI/NLP researcher** — read ARCHITECTURE.md §12–§13 (AI
resources, benchmarks). The `ai/` and `benchmarks/` layers are designed for
you.

**If you represent an organization** considering adopting SLS — read
ARCHITECTURE.md Part II (§22–§32), which defines the numbered standards
catalog and the compliance model you would implement against.

## Development workflow

The project remains documentation- and data-first. Its first executable build
surface is the Rust schema validator under `tools/validators/`.

1. **Fork and clone** the repository.
2. **Create a branch** using the naming convention in
   [CONTRIBUTING.md](../CONTRIBUTING.md#branch-naming).
3. **Make your change** following the [Style Guide](STYLE_GUIDE.md).
4. **Run the current local checks**:

   ```bash
   cargo test --workspace --offline
   cargo run --offline -p sls-validators -- check --root .
   ```
5. **Commit with a DCO sign-off**: `git commit -s`.
6. **Open a pull request** and fill in the template.
7. The repository checker already performs schema and cross-reference
   validation locally. GitHub CI enforcement is the remaining Phase 4 step.

Structural changes (new spec docs, new domains, schema changes) must start as
a GitHub Discussion or issue — see the
[two contribution tracks](../CONTRIBUTING.md#the-two-contribution-tracks).
